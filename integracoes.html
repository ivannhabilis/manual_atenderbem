Integrações e Automações Externas

Referência operacional para conectar canais, ERPs, formulários, planilhas e bases analíticas sem perder segurança, rastreabilidade e consistência dos dados.

Valide na sua instância antes de implantar: a documentação de Generic Queue 2 descreve um recurso técnico que pode ser legado, experimental ou não estar habilitado em todas as versões. Confirme com o administrador ou suporte a disponibilidade, os campos exibidos, a URL de webhook gerada e o contrato vigente. Não presuma que exemplos deste capítulo representam o estado atual da sua instalação.
Exemplos seguros: todos os domínios, identificadores, números e chaves abaixo são fictícios. Nunca copie uma URL real de webhook, token, chave JSON, telefone de cliente ou credencial para documentação, chamados, capturas de tela ou repositórios.

1. Arquitetura e escolha da integração

Uma integração liga a plataforma a outro sistema para que dados e ações circulem sem digitação repetida. O mecanismo correto depende de quem inicia a comunicação, da urgência e do volume.

MecanismoDireção típicaUse quandoPonto de atenção
Requisição HTTPAutomação → sistema externoÉ preciso consultar ou alterar um ERP, CRM ou serviço durante o fluxo.Timeout, autenticação, contrato do payload e tratamento de falhas.
Captura de WebhookSistema externo → plataformaO sistema de origem deve notificar um evento em tempo real.URL exclusiva, autenticação, repetição de eventos e validação de origem.
API nativaBidirecionalO integrador precisa criar, consultar ou atualizar registros de forma controlada.Use a documentação disponível em Filas › Documentação da API da própria instância.
Generic Queue 2Canal externo ⇄ filaUm sistema de mensagens externo precisa operar como canal de atendimento.Recurso técnico/possivelmente legado; valide disponibilidade e contrato na instância.
Sincronização BigQueryPlataforma → Google CloudO objetivo é análise histórica, BI e processamento de grande volume.Custo de streaming/consulta, permissões da conta de serviço e política de retenção.

Padrão recomendado para CRM e ERP

  1. Defina uma chave de associação única: grave, nos dois sistemas, um identificador estável, como o ID da Oportunidade. Não use nome ou telefone como única chave de vínculo.
  2. Envie mudanças em tempo real: em eventos de ganho, perda, entrada, saída ou estagnação, uma automação pode chamar a API do ERP.
  3. Faça reconciliação periódica: consulte o registro externo, compare os dados com Código JS e atualize apenas campos divergentes.
  4. Receba mudanças externas: o ERP pode chamar a API nativa ou uma Captura de Webhook vinculada a um fluxo.
  5. Registre correlação: salve IDs dos dois lados, horário, operação e resultado para permitir auditoria e reprocessamento.
Anexos em oportunidades: a sequência indicada no material técnico é enviar o arquivo por uploadFile, consultar a oportunidade com getOpportunity, acrescentar o novo ID à lista existente e atualizar a lista completa com updateOpportunity. Confirme nomes, autenticação e schemas na documentação da API da sua instância antes de usar.

2. Generic Queue 2

A Generic Queue 2 é descrita no material técnico como uma interface REST para transformar um sistema de mensagens externo em uma fila bidirecional. O contrato contempla texto, mídia, localização, interações, citações, leitura e estados de entrega.

2.1. Parâmetros documentados

CampoObrigatórioFinalidade
serverurlSimURL base do servidor do integrador, para onde a fila envia mensagens e eventos.
apikeySimChave usada no esquema documentado de autenticação nas duas direções.
sourceSimIdentificador único do canal externo, como número ou ID de conta.

Depois da criação, o material informa que a plataforma fornece uma URL única de webhook. O integrador envia para essa URL os eventos de mensagem recebida e de alteração de status. A URL exata deve ser copiada da própria instância e tratada como informação sensível.

2.2. Fluxo bidirecional

OrigemDestinoOperação documentadaUso
PlataformaServidor do integradorPOST /messagesSolicita o envio de uma mensagem ao destinatário externo.
PlataformaServidor do integradorPOST /messages/readInforma que uma mensagem foi marcada como lida.
Servidor do integradorWebhook da filamessage.receivedEntrega à plataforma uma mensagem recebida no canal externo.
Servidor do integradorWebhook da filamessage.statusAtualiza o estado de uma mensagem para sent, delivered, read ou failed.

2.3. Autenticação e respostas

O contrato fornecido usa o header Authorization em todas as requisições. Armazene a chave em cofre ou variável de ambiente, nunca no código-fonte.

Authorization: Bearer <CHAVE_ARMAZENADA_EM_SEGREDO>
Content-Type: application/json

Em caso de sucesso no envio, o servidor pode conservar o messageId recebido ou retornar o ID gerado pelo canal externo:

{
  "success": true,
  "messageId": "canal_msg_01JEXEMPLO"
}

Para falhas permanentes de negócio, o material descreve uma resposta estruturada. O código abaixo é ilustrativo e não contém dados reais:

{
  "success": false,
  "error": {
    "code": "INVALID_RECIPIENT",
    "message": "Destinatário inválido para este canal"
  }
}

2.4. Payloads mínimos seguros

Mensagem de saída recebida pelo servidor do integrador em POST /messages:

{
  "event": "message.send",
  "messageId": "msg_01JEXEMPLO",
  "from": "canal_exemplo_001",
  "to": "contato_exemplo_042",
  "timestamp": 1735603200,
  "type": "text",
  "content": {
    "text": "Olá, como posso ajudar?"
  }
}

Mensagem de entrada enviada pelo integrador para a URL de webhook fornecida pela instância:

{
  "event": "message.received",
  "messageId": "externo_01JEXEMPLO",
  "from": "contato_exemplo_042",
  "to": "canal_exemplo_001",
  "timestamp": 1735603200,
  "type": "text",
  "content": {
    "text": "Preciso consultar meu pedido."
  }
}

Atualização de falha:

{
  "event": "message.status",
  "messageId": "canal_msg_01JEXEMPLO",
  "from": "contato_exemplo_042",
  "status": "failed",
  "timestamp": 1735603260,
  "error": {
    "code": "RECIPIENT_UNAVAILABLE",
    "message": "Destinatário indisponível"
  }
}

Mídia: embora o material original mencione token na query string, prefira URLs assinadas, de curta duração e com escopo somente de leitura. Parâmetros de URL podem aparecer em logs, histórico e ferramentas de monitoramento. Não exponha credenciais permanentes nem permita que a URL acesse outros arquivos.

3. Requisições HTTP, webhooks e automações

Os fluxos de automação podem combinar Requisição HTTP para enviar ou buscar dados, Código JS para transformar variáveis e Captura de Webhook para receber eventos externos. Automações podem ser acionadas por eventos de oportunidade — ganho, perda, atraso, entrada, saída e estagnação — ou executadas periodicamente.

3.1. Publicar um endpoint receptor

  1. Defina o contrato: método, caminho, headers, schema, códigos HTTP e limite de tamanho.
  2. Proteja o endpoint: aceite somente HTTPS, valide autenticação antes do corpo e aplique limite de requisições.
  3. Valide a entrada: rejeite campos ausentes, tipos inválidos, eventos desconhecidos e identificadores fora do escopo.
  4. Garanta idempotência: registre messageId ou outro ID do evento; repetição deve devolver sucesso sem repetir o efeito.
  5. Responda rápido: confirme o recebimento e processe tarefas longas em fila interna, quando a arquitetura permitir.
  6. Registre com segurança: use ID de correlação, código HTTP, duração e resultado; mascare tokens, telefones, conteúdo e dados pessoais.

3.2. Enviar dados por uma automação

Monte o payload apenas com os campos necessários e utilize um domínio fictício durante a especificação:

POST https://api.exemplo.invalid/v1/oportunidades/sincronizar
Authorization: Bearer <SEGREDO_FORA_DO_FLUXO_E_DOS_LOGS>
Content-Type: application/json
Idempotency-Key: oportunidade-9001-versao-7

{
  "opportunityId": 9001,
  "externalId": "erp-negocio-2042",
  "status": "ganha",
  "updatedAt": "2026-09-14T15:00:00Z"
}
O domínio especial .invalid é usado aqui para impedir chamadas acidentais. Substitua-o somente em ambiente controlado, depois da homologação do contrato e da autorização do proprietário do sistema externo.

3.3. Semântica de erro e repetição

No contrato documentado da Generic Queue 2, falhas de rede, timeout de 30 segundos e respostas 5xx acionam repetição com backoff exponencial, chegando a até 15 tentativas ao longo de aproximadamente três horas. Respostas 4xx não são repetidas; inclusive 429 é listado como falha sem retry nesse contrato específico.

SituaçãoResposta recomendada no contrato GQ2Ação operacional
Payload inválido ou campo ausente400Corrigir o emissor; repetição automática não resolve.
Chave ausente ou inválida401Conferir segredo e prefixo Bearer; rotacionar se houver suspeita.
Ação fora do escopo403Revisar permissões sem ampliar acesso desnecessariamente.
Limite excedido429Reduzir a taxa no emissor; não contar com retry automático da GQ2.
Falha transitória do receptor503Permitir a repetição automática e monitorar recuperação.
Erro permanente de negócio200 com success: false, conforme material GQ2Registrar código de aplicação e não processar novamente.
Não generalize: a semântica acima é do contrato fornecido para Generic Queue 2. Outras APIs podem exigir códigos e políticas diferentes. Leia sempre a documentação da integração alvo.

4. Google Forms para Captura de Webhook

O fluxo documentado envia as respostas de um Google Form para uma Captura de Webhook da instância por meio do Google Apps Script.

  1. Na plataforma: crie uma Captura de Webhook em Configurações › Automação › Captura de Webhook; copie a URL e a chave para um cofre temporário.
  2. No Google Forms: abra o formulário com a conta proprietária e acesse Apps Script.
  3. No script: configure a URL e a autenticação usando propriedades protegidas do projeto, sem gravar segredos diretamente no código.
  4. Nos acionadores: adicione um acionador para a função onSubmit com o tipo de evento Ao enviar formulário e conceda apenas as permissões necessárias.
  5. Homologue: envie uma resposta fictícia, confirme o recebimento na captura e valide os nomes e tipos das perguntas.

Exemplo adaptado sem segredo embutido

function onSubmit(e) {
  const props = PropertiesService.getScriptProperties();
  const postUrl = props.getProperty('WEBHOOK_URL');
  const apiKey = props.getProperty('WEBHOOK_API_KEY');
  const forms = {};

  e.response.getItemResponses().forEach(function (itemResponse) {
    const question = itemResponse.getItem().getTitle();
    forms[question] = itemResponse.getResponse();
  });

  UrlFetchApp.fetch(postUrl, {
    method: 'post',
    contentType: 'application/json',
    headers: { Authorization: 'Bearer ' + apiKey },
    payload: JSON.stringify(forms),
    muteHttpExceptions: true
  });
}
Por que usar o evento e? o material-base consulta todas as respostas e escolhe a última. Em submissões próximas, isso pode associar o evento à resposta errada. Usar e.response vincula o processamento à resposta que acionou a função. Valide essa abordagem no Apps Script do formulário antes de publicar.
Os títulos das perguntas viram chaves JSON. Renomear uma pergunta altera o contrato. Para integrações duráveis, mapeie cada título para um nome técnico estável e não envie respostas sensíveis sem base legal, finalidade e retenção definidas.

5. Consulta ao Google Sheets

O material de apoio apresenta a API Google Sheets v4 para consultar um intervalo de células. O formato documentado é:

GET https://sheets.googleapis.com/v4/spreadsheets/<ID_DA_PLANILHA>/values/<ABA>!<INICIO>:<FIM>?key=<CHAVE>

Exemplo fictício, deliberadamente não funcional:

GET https://sheets.googleapis.com/v4/spreadsheets/ID_PLANILHA_EXEMPLO/values/Clientes!A2:F200?key=CHAVE_RESTRITA

5.1. Configuração orientada pelo material

  1. No Google Cloud, selecione o projeto responsável pela integração.
  2. Em APIs e serviços, habilite a Google Sheets API.
  3. Crie a credencial adequada e aplique restrições de API, origem e uso sempre que disponíveis.
  4. Obtenha o ID da planilha, o nome exato da aba e o intervalo necessário.
  5. Configure a Requisição HTTP no fluxo e trate a matriz values retornada.

5.2. Compartilhamento e segurança

O tutorial de apoio sugere liberar a planilha para “qualquer pessoa com o link” em modo leitura. Isso torna o conteúdo acessível a quem obtiver o link e não deve ser o padrão para dados de clientes, atendimentos ou operação. Em produção, prefira identidade autenticada, conta de serviço ou OAuth com menor privilégio e compartilhe a planilha somente com essa identidade. Se a integração disponível na instância aceitar apenas chave de API e conteúdo público, use uma planilha exclusiva, sanitizada e sem dados pessoais; valide o risco com segurança e privacidade.
  • Limite o intervalo: consultar A2:F200 é mais previsível que linhas ou colunas inteiras.
  • Não coloque chaves em mensagens, prints, parâmetros registrados em logs ou código público.
  • Restrinja a chave à Sheets API e às origens permitidas quando o Google Cloud oferecer essa opção.
  • Defina cabeçalhos estáveis e trate linha vazia, coluna ausente e alteração de ordem.
  • Use cache e periodicidade razoável para evitar cota excedida e latência no atendimento.

6. Google Cloud e BigQuery

O BigQuery recebe dados da plataforma para análise em SQL, BI e processamento em escala. O material informa que a sincronização cria um dataset com tabelas do sistema e ocorre diariamente de madrugada.

6.1. Preparação do projeto

  1. Crie ou selecione o projeto: copie o ID do projeto; ele será usado no campo ProjectID do BigQuery.
  2. Prepare uma conta de serviço: conceda somente as permissões necessárias para criar/escrever no dataset previsto. O material cita Proprietário de Dados BigQuery, mas esse papel é amplo; valide um conjunto de menor privilégio com a equipe Google Cloud.
  3. Crie uma chave JSON apenas se exigida: baixe-a em estação segura, limite o acesso e defina rotação. Prefira credenciais de curta duração quando a arquitetura da instância oferecer essa alternativa.
  4. Habilite faturamento e orçamento: o material alerta que inserções de streaming geram custo e não são compatíveis com uma operação estritamente gratuita. Configure alertas de orçamento antes da sincronização.
  5. Na plataforma: acesse Configurações › Geral, preencha ProjectID do BigQuery e Auth Key, e salve.
  6. Valide a primeira carga: confira dataset, tabelas, datas, quantidade aproximada de registros e política de localização/retenção.
Auth Key é segredo: o JSON pode conter uma chave privada. Cole-o somente no campo oficial da instância; nunca o anexe a chamado, e-mail, documento ou repositório. Se houver exposição, revogue a chave no Google Cloud, crie outra e atualize a integração.

6.2. Registros atualizados e histórico

Opção “Excluir registros atualizados”Comportamento descritoIndicação
MarcadaAo sincronizar a versão nova de um atendimento, o registro antigo é removido e permanece o estado mais recente.Visão operacional atual, menor duplicidade aparente.
DesmarcadaAs versões são acumuladas; um atendimento aberto hoje e fechado amanhã pode aparecer em dois registros.Análise histórica, desde que as consultas saibam escolher a versão correta.

Ao trocar o projeto de uma instância já sincronizada, o material orienta substituir os dados, acionar Limpar sincronização e reiniciar a instância. Essa é uma operação administrativa com impacto; agende janela, registre o projeto anterior e confirme com suporte o procedimento vigente antes de executar.

6.3. Usos e controles

  • Conectar Looker Studio, Tableau, Power BI ou Google Sheets para visualização, respeitando os controles de acesso.
  • Executar SQL e rotinas de ETL; evitar SELECT * em tabelas grandes para reduzir custo.
  • Particionar e filtrar por data quando a estrutura das tabelas permitir.
  • Monitorar custo de armazenamento, streaming e bytes processados por consulta.
  • Separar ambientes e projetos de homologação e produção.
  • Documentar quais tabelas contêm dados pessoais e quem pode consultá-las.

7. Variáveis em templates

Para templates da Meta usados pela fila WhatsApp Cloud API, o material específico informa suporte, no sistema, a variáveis posicionais numéricas — {{1}}, {{2}} e assim por diante — e alerta que variáveis do tipo nome não são suportadas nesse fluxo documentado.

  1. Na Meta: crie o template usando placeholders numéricos sequenciais e informe valores de exemplo durante a submissão.
  2. No sistema: no campo Corpo do template, use o mesmo nome posicional definido na Meta, como {{1}}.
  3. No valor do parâmetro: associe a variável interna que fornecerá o conteúdo em tempo de envio.
  4. Teste: confira ordem, conteúdo ausente, tamanho e formatação com dados fictícios antes do disparo real.

Exemplo conceitual

CamadaConfiguração fictícia
Corpo aprovado na MetaOlá! O pedido {{1}} está com o status {{2}}. Consulte os detalhes no portal.
Nome do parâmetro 1 no sistema{{1}}
Valor do parâmetro 1Variável interna que contém o identificador do pedido.
Nome do parâmetro 2 no sistema{{2}}
Valor do parâmetro 2Variável interna que contém o status do pedido.
Não misture contratos: a Meta pode oferecer outros formatos na interface, mas o material do sistema registra suporte apenas a placeholders numéricos para esse fluxo. Valide isso na fila e na versão atuais. Nunca use variável para inserir senha, token, cartão completo, documento ou outro dado sensível em mensagem.

8. Segurança, privacidade e governança

ControleAplicação prática
HTTPSExija TLS válido em endpoints, webhooks e mídias; não use HTTP ou localhost fora de laboratório isolado.
Menor privilégioUma chave por fila/integração, conta de serviço dedicada e permissões somente nos recursos necessários.
Gestão de segredosCofre ou variável de ambiente; rotação periódica e imediata após suspeita de exposição.
ValidaçãoConfira autenticação, evento, schema, tamanho, source/to, tipo de mídia e domínio de URL.
IdempotênciaArmazene o ID do evento com expiração adequada e impeça efeitos duplicados.
Proteção contra SSRFSe o sistema baixa URLs de mídia ou consulta URLs recebidas, use allowlist de hosts, bloqueie redes privadas/loopback e limite redirecionamentos.
Logs mínimosRegistre metadados operacionais, não corpos completos; mascare Authorization, query strings e dados pessoais.
LGPD e retençãoDefina finalidade, base legal, acesso, prazo de retenção, descarte e resposta a solicitações do titular.
Separação de ambientesFilas, endpoints, projetos, chaves e dados distintos para homologação e produção.
Plano de revogaçãoMantenha procedimento para desativar captura, revogar chave, interromper automação e reprocessar eventos.

Checklist antes de liberar produção

  1. Responsável técnico e proprietário dos dados identificados.
  2. Contrato de campos, tipos, códigos HTTP e versionamento aprovado.
  3. Segredos exclusivos, armazenados corretamente e testados sem aparecer em logs.
  4. Teste de evento duplicado, ordem invertida, timeout, 4xx, 5xx e mídia indisponível.
  5. Alertas para aumento de falhas, latência, fila acumulada, cota e custo.
  6. Plano de rollback e janela de mudança definidos.
  7. Dados fictícios usados na homologação; qualquer dado real autorizado e minimizado.

Sequência de diagnóstico

  1. Correlacione: localize um único evento pelo messageId, ID da oportunidade ou ID de execução.
  2. Confirme a direção: determine se a falha está na saída da plataforma, no receptor externo ou no retorno por webhook.
  3. Cheque transporte: DNS, certificado TLS, método, caminho, timeout e código HTTP.
  4. Cheque autenticação: identidade, escopo e validade sem revelar o segredo.
  5. Cheque contrato: evento, campos, tipos, encoding, tamanho e versão.
  6. Cheque efeito: confirme no sistema de destino se a operação ocorreu antes de reprocessar.
  7. Documente: registre causa, impacto, IDs de correlação, correção e prevenção; remova qualquer dado sensível.

10. Boas práticas de implementação

  • Comece pequeno: na Generic Queue 2, homologue texto e status antes de mídia, botões, listas e citações.
  • Versione o contrato: mudanças de campo não devem quebrar consumidores existentes.
  • Use IDs globais e imutáveis: nunca reutilize messageId; mantenha o mapeamento com o ID externo.
  • Projete para repetição: webhooks e automações distribuídas podem ser entregues mais de uma vez.
  • Não confunda aceite com conclusão: resposta HTTP de sucesso confirma o recebimento; use estados e reconciliação para confirmar o efeito final.
  • Respeite a ordem de status: sent → delivered → read; failed deve conter código e mensagem úteis, sem dados sensíveis.
  • Defina timeouts: o material GQ2 cita 30 segundos para requisições e 60 segundos para downloads de mídia; valide os limites reais da versão em uso.
  • Evite dependência de texto visível: use IDs técnicos de botão, lista, oportunidade, usuário e arquivo.
  • Reconcilie: uma rotina periódica detecta eventos perdidos e divergências entre CRM, ERP e base analítica.
  • Monitore custo e capacidade: cotas do Google, volume de BigQuery, armazenamento de mídia e acúmulo de retries.
  • Mantenha runbook: inclua contatos, dashboards, como pausar, como rotacionar segredo e como reprocessar com segurança.
Critério de aceite: considere a integração pronta somente quando um caso completo tiver sido comprovado nos dois sentidos, com autenticação, idempotência, falha controlada, auditoria e leitura do estado final no sistema de destino.
