WebChat V2: identidade do visitante

O identificador do visitante é público por natureza. Esta é a camada que impede alguém de usar o identificador de outra pessoa para abrir o atendimento e o histórico dela.

1. O problema, em uma frase

O widget guarda no navegador um clientId — o identificador daquele visitante. Quando o site fixa esse identificador (por exemplo, com o e-mail, o telefone, o documento ou o código do usuário logado), qualquer pessoa que descubra o valor pode tentar se passar pelo cliente. E identificadores derivados de dado do cliente são adivinháveis: telefone, e-mail e documento são fáceis de obter.

A defesa não é esconder o identificador: é exigir prova de posse antes de entregar a sessão que já tem atendimento ou histórico.

2. As duas provas aceitas

ProvaQuem produzCobreValidade
Token de sessãoO servidor da plataforma entrega a cada conexão; o widget com suporte guarda e reapresentaO mesmo navegador, sem nenhum trabalho no site180 dias, renovado a cada conexão
Assinatura do clientIdO servidor do site, com a chave da filaOutro dispositivo ou navegador, que ainda não tem tokenEnquanto a chave for aceita — a assinatura não expira

3. Gerar e guardar a chave

  1. Gere a chave com webchat_identity_rotate_secret {queueId} — 64 caracteres hexadecimais, devolvidos uma única vez. Não existe forma de lê-la depois.
  2. Guarde no servidor do site: variável de ambiente ou cofre de segredos. Nunca no HTML, nunca no JavaScript da página, nunca em repositório de front-end — quem lê a página leria a chave.
  3. Rotacione sem quebrar: ao gerar uma chave nova, a anterior passa a “anterior” e continua aceita. Atualize o servidor, acompanhe stats.signatureKeys.previous parar de crescer e só então descarte com webchat_identity_drop_previous_secret (exige confirm: true).
  4. Só duas valem ao mesmo tempo. Gerar outra chave enquanto existe uma anterior guardada descarta a anterior na hora — nesse caso a ferramenta exige confirm: true.

4. Assinar corretamente

Três detalhes decidem se a assinatura vale:

  • Algoritmo: HMAC-SHA256 em hexadecimal minúsculo. O prefixo opcional sha256= é aceito.
  • Chave: o texto da chave exatamente como entregue, em bytes UTF-8. Não decodifique o hexadecimal — se você transformar os 64 caracteres em 32 bytes, a assinatura nunca casa.
  • Mensagem: o clientId exato que a página vai fixar — mesma caixa, mesmos caracteres, sem espaços sobrando.
// Node.js
const { createHmac } = require("crypto");
const assinatura = createHmac("sha256", CHAVE).update(clientId, "utf8").digest("hex");

// PHP
$assinatura = hash_hmac("sha256", $clientId, $chave);

# Python
import hmac, hashlib
assinatura = hmac.new(chave.encode("utf-8"), client_id.encode("utf-8"), hashlib.sha256).hexdigest();

// C#
var assinatura = Convert.ToHexString(
    new HMACSHA256(Encoding.UTF8.GetBytes(chave)).ComputeHash(Encoding.UTF8.GetBytes(clientId))
).ToLowerInvariant();

// Java
Mac m = Mac.getInstance("HmacSHA256");
m.init(new SecretKeySpec(chave.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
String assinatura = HexFormat.of().formatHex(m.doFinal(clientId.getBytes(StandardCharsets.UTF_8)));

5. Entregar ao widget

O servidor do site gera a página já com o par pronto. O detalhe que costuma quebrar a integração: o embed carrega o widget de forma assíncrona, então window.omniChat ainda não existe quando o script da página roda. Espere o carregador:

<script>
(function boot() {
  if (!window.omniChat) return setTimeout(boot, 50);
  window.omniChat.identify("<clientId>", "<assinatura>");
})();
</script>
  • identify pode ser chamado antes ou depois de a configuração do widget carregar — se for antes, é aplicado quando ela chega.
  • As propriedades window.omniChat.clientId e window.omniChat.clientIdSignature só valem depois do evento configLoaded; antes, são ignoradas sem erro. Prefira identify.
  • A assinatura vale para aquele clientId. Trocar o identificador exige assinar de novo.
  • Exige widget com suporte à identidade (identityVersion 1) e servidor atualizado antes de o widget novo ser publicado.

6. Modo estrito

Sem prova, a plataforma já não entrega sessão limpa para um identificador que tem histórico — mas ainda restam frestas: um identificador em formato UUID, sem assinatura, pode ser reservado por quem o usar primeiro. O modo estrito fecha isso.

SituaçãoModo compatível (padrão)Modo estrito
UUID sem assinatura, sem históricoMantidoIdentidade nova
Identificador que não é UUID, sem assinaturaIdentidade nova a cada conexãoIdentidade nova, sempre
Identidade com atendimento ou histórico, sem provaIdentidade novaIdentidade nova
Sessão antiga sem prova, no momento em que o estrito é ligado—Identidade nova, uma única vez
  • Liga e desliga por fila com webchat_identity_set_strict {queueId, strict} — vale na hora, sem reinício. Quando a instância inteira está em modo estrito, todas as filas de WebChat seguem o modo, independentemente do valor da fila.
  • O campo equivalente na fila é webchatIdentityStrict (visível em queues_get/queues_update).
  • Ligue só depois de gerar a chave e de o site assinar. Ligar antes transforma cada visitante em visitante novo — o histórico some para ele (e continua no painel).

7. Como decidir com os contadores

webchat_identity_get devolve, por fila de WebChat V2, o modo da instância, o modo da fila, o efetivo, se existem chaves (atual, anterior, do operador) e contadores desde o último reinício. É com eles — não com achismo — que se decide ligar o estrito.

{
  "instanceMode": "compat",
  "queues": [
    {
      "queueId": 123,
      "queueStrict": 0,
      "effectiveStrict": false,
      "hasSecret": true,
      "hasPreviousSecret": false,
      "activeField": "",
      "stats": {
        "total": 412,
        "capable": 386,
        "reasons": {"compat-unproven-state": 12, "signature-invalid": 0, "signature": 141},
        "capableReasons": {"signature": 141, "token": 233}
      }
    }
  ]
}
  • Critério de prontidão: capable próximo de total (o widget com suporte já está publicado) e, nas filas em que o site fixa o identificador, reasons.signature maior que zero com signature-invalid em zero.
  • compat-unproven-state e token-unclean não convergem para zero e não servem de critério: eles medem o custo de ligar o estrito, uma vez. Servem para dimensionar o impacto.
  • Motivos possíveis: token, token-unclean, signature, signature-invalid, migration, compat-unproven (fila V1 ou widget antigo), compat-unproven-state, compat-unproven-stateless, strict-stateless, strict-new-identity, strict-token-unclean e strict-unsigned-id (identificador que não é UUID, trocado pelo estrito).
  • Os contadores são em memória, desde o último reinício — zere a expectativa depois de qualquer manutenção.

8. Ativo por campo do contato

Quando um atendimento ativo é aberto informando só o contato (pelo painel ou pela abertura ativa por API), o identificador do visitante pode ser um campo do contato. É o que a chave webchatActiveField da fila decide:

ValorIdentificador usadoObservação
"" (padrão)Automático: ligações já gravadas e o UUID do contatoComportamento histórico, sem mudança
number / telefoneTelefone do contatoAdivinhável
E-mailE-mail do contatoAdivinhável
DocumentoCPF/CNPJ do contatoAdivinhável
Código externo / campo personalizadoO valor gravado no contatoAdivinhável
Campo adivinhável só com o estrito ligado e o site assinando. Sem a assinatura, no modo estrito, nem o próprio cliente entra no atendimento ativo apontado para telefone, e-mail ou documento. O UUID do contato é o único campo que não se adivinha.

9. Vínculos de visitante do contato

Cada navegador reconhecido como o contato numa fila de WebChat V2 é uma ligação registrada — e ligação feita por engano precisa de saída.

  • contacts_webchat_ids_list {id} lista até 200 ligações do contato, mais recentes primeiro, com fila, clientId, origem (associação no painel, abertura ativa, integração) e datas.
  • contacts_webchat_ids_remove {id, linkId} desfaz uma ligação: o navegador deixa de ser reconhecido como o contato naquela fila e os atendimentos encerrados daquele identificador somem do histórico do visitante — o atendimento continua existindo no contato. Atendimento aberto no momento não é afetado.
  • “Invalidar sessões de WebChat” no contato não revoga o token de um identificador fixado pelo site.

10. Limites e o que não se resolve aqui

  • A assinatura não expira: vale enquanto a chave for aceita. Se a chave vazar, gere outra e descarte a anterior.
  • O token de sessão vale 180 dias por padrão e é renovado a cada conexão.
  • Um identificador que não é UUID, sem assinatura, nunca recebe sessão limpa — nem quem o usar antes do cliente.
  • O modo da instância (instanceMode) e as chaves do operador (hasConfSecret) são configuração de servidor, fora do alcance das ferramentas de integração: quem administra a instância define.
  • WebChat V1 não participa desse mecanismo — as filas aparecem como compat-unproven no diagnóstico.
