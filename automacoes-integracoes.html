request

Envia uma requisição HTTP para um servidor externo. O resultado da requisição é salvo em variáveis e pode ser utilizado em outras partes do fluxo de execução.

É feito um parse no retorno da requisição, se este for do tipo JSON ou multipart/form-data, o resultado é convertido para objeto JavaScript e disponibilizado em uma variável.
As seguintes variáveis são criadas automaticamente:
varPrefix + _httpStatus: Código de status da resposta da requisição. Exemplo de nome final da varíavel com prefixo: "req_response_httpStatus"
varPrefix + _rawBody: Corpo bruto da resposta da requisição. Exemplo de nome final da varíavel com prefixo: "req_response_rawBody"
varPrefix + _parsedBody: Corpo da resposta da requisição convertido para objeto JavaScript quando possível. Exemplo de nome final da varíavel com prefixo: "req_response_parsedBody"
Adicionalmente, se o tipo de resposta (expectedContentType) estiver configurado para 2 (salvar como arquivo), também é criada a variável varPrefix + _fileId com o ID do arquivo gerado com o resultado da requisição.

publishToExtension

Publica uma mensagem no CANAL de uma INSTALAÇÃO DE EXTENSÃO, entregue em tempo real às telas dos usuários de destino. Serve para o fluxo avisar a interface de uma extensão de que algo aconteceu no servidor — por exemplo "o título foi pago, busque os dados de novo".

O canal é de MELHOR ESFORÇO e sem retenção de nenhuma espécie: não há ordenação garantida, não há entrega para quem está desconectado, não há repetição e não há confirmação. Quem só começar a ouvir depois da publicação simplesmente não recebe aquela mensagem — a extensão precisa saber buscar o estado atual por conta própria.
O ALVO É OBRIGATÓRIO e nunca assume "todos": publicar sem alvo seria transformar uma mensagem dirigida a um usuário em difusão para a instância inteira. Formatos aceitos: "user:{id}" (um usuário), "users:[1,2,3]" (vários), "type:agent" | "type:supervisor" | "type:admin" (por perfil), "queue:{id}" (quem atende ou supervisiona a fila), "group:{id}" (quem está no grupo) e "all" (todos, escolha explícita).
A entrega respeita a permissão: só recebe a mensagem quem já recebe aquela instalação da extensão, conforme os filtros configurados na instalação.
O PAYLOAD DEVE LEVAR IDENTIFICADORES, NUNCA DADOS. A mensagem atravessa a fronteira de permissão e o servidor não interpreta o conteúdo para filtrar nada: publique {"pedidoId": 4471} e deixe que cada tela busque o pedido com a permissão de quem está logado. Publicar o pedido inteiro entregaria a usuários diferentes um conteúdo que talvez nenhum deles pudesse ver. O tamanho é limitado a 4 KB, justamente para tornar desconfortável publicar dados.
Há limite de taxa por instalação. O estouro repetido desliga o canal daquela instalação (disjuntor), e a extensão deixa de receber até que alguém rearme o canal na tela de administração de extensões. Não publique dentro de laços nem a cada mensagem recebida.
O elemento nunca interrompe o fluxo: alvo vazio, instalação inexistente, JSON inválido no payload ou recusa do canal são registrados na depuração da automação e o fluxo segue para o próximo elemento.

Exemplos de uso

Fluxos completos que usam os elementos deste grupo. Cada exemplo foi compilado pelo próprio sistema antes de entrar aqui.

Consultar uma API externa, decidir pelo status e avisar a extensao

Consultar o status de um pedido numa API externa, ramificar pelo codigo HTTP e publicar o resultado no canal de uma extensao instalada.

  1. request — faz um GET no endpoint externo e guarda a resposta em variaveis com o prefixo pedido (pedido_status, pedido.*).
  2. varCondition — ramifica por expressao: se pedido_status == 200 segue o caminho de sucesso, senao o de falha.
  3. message — confirma ao cliente que o pedido foi consultado.
  4. publishToExtension — publica no canal da extensao painel-pedidos, no topico pedido_atualizado, avisando os agentes para recarregar os dados.
  5. terminate — encerra o atendimento pelos dois caminhos.
consulta: request dataType="json" method="get" url="https://api.exemplo.com/pedidos/{{chat_protocol}}" varPrefix="pedido"
checa: varCondition {
  case ok conditionOperator="expression" conditionValue="pedido_status == 200" {
    bom: message text="Seu pedido foi consultado com sucesso."
    avisa: publishToExtension installId="painel-pedidos" topic="pedido_atualizado" target="type:agent" payload="{\"chatId\": \"{{chat_id}}\"}"
    f1: terminate reason="Pedido consultado"
  }
  else {
    ruim: message text="Nao consegui consultar seu pedido agora. Vou encaminhar para um atendente."
    f2: terminate reason="Falha na consulta"
  }
}
Resultado: Se a API responde 200, o cliente ve a confirmacao e a extensao painel-pedidos recebe o aviso; senao o cliente e orientado.

Responder a um webhook com JSON e gerar QR Code de um link

Responder a uma captura de webhook com um JSON de confirmacao e gerar o QR Code de um link de acompanhamento.

  1. webhookReply — define a resposta HTTP enviada a quem chamou o webhook: status 200 e um JSON de confirmacao com o protocolo.
  2. generateQrCode — gera o QR Code do link de acompanhamento e guarda o ID do arquivo em qrcode_file_id.
  3. message — avisa o cliente que o QR Code foi enviado.
  4. terminate — encerra o atendimento.
responde: webhookReply httpStatus=200 contentType="application/json" content="{\"status\":\"ok\",\"protocolo\":\"{{chat_protocol}}\"}"
qrcode: generateQrCode content="https://exemplo.com/acompanhar/{{chat_protocol}}" resultVariableName="qrcode_file_id"
envia: message text="Segue o QR Code para acompanhar seu pedido."
fim: terminate reason="Webhook respondido e QR Code gerado"
Resultado: Quem chamou o webhook recebe o JSON {"status":"ok",...} e o cliente recebe o QR Code do link de acompanhamento.
