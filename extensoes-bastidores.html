Extensões: Bastidores do Projeto

Como este material foi produzido: as fontes de verdade, o método de investigação, o teste do ciclo de vida, as armadilhas encontradas e as regras de ouro. Serve como roteiro reaproveitável para entender e documentar qualquer módulo da plataforma.

Por que existir esta página: o módulo de Extensões junta, sob um único nome, três papéis diferentes (criar, instalar, distribuir). A confusão é natural. Este capítulo mostra como desmontamos essa confusão — método, provas e tropeços —, para que o mesmo caminho sirva a outros assuntos.

1. O ponto de partida

A dúvida que originou tudo: um usuário Administrador enxerga a tela de Extensões, um superusuário enxerga a tela de Extensões instaladas, e sem um acesso de superusuário na própria instância ficava a pergunta: como o Administrador cria as extensões?

A resposta não estava em nenhum lugar só. Foi preciso cruzar várias fontes — e provar fazendo.

2. As fontes de verdade (a ordem importa)

  1. A instância ao vivo. A única fonte que não mente. Consultamos a API de configuração da própria plataforma e descobrimos quem o chamador é (um perfil interno de superusuário) — o que explica por que a integração consegue fazer o que o Administrador não consegue.
  2. A lista de ferramentas da plataforma. Ao separá-las por assunto, ficou evidente que existem duas famílias: uma de autoria (editor) e outra de instalação. Só esse fato já provava que criar e instalar são coisas distintas.
  3. A interface gráfica real. Entrar como Administrador e olhar os menus mostrou que o item Extensões abre o editor; tentar abrir a tela de instalações resulta em redirecionamento — não é "escondido", é proibido.
  4. A documentação que o produto carrega dentro de si. A aplicação web baixa no navegador o próprio manual do desenvolvedor. Ali está a frase decisiva: a administração de extensões é exclusiva de superusuário, e um Administrador comum recebe 403 inclusive para leitura.
  5. Os dados reais. O que já existia na instância (extensões no editor, instalações, ponteiros) confirmou o modelo: um mesmo aplicativo, várias instalações independentes.
Método: nunca decidir por uma fonte só. Quando a documentação, a interface e os dados concordam, o entendimento está firme; quando divergem, é ali que mora a pegadinha.

3. O modelo mental que resolve a confusão

Pense numa loja de aplicativos: o aplicativo existe uma vez só na loja (global); cada aparelho que instala tem a sua cópia, com os seus dados (local).

PapelTelaQuem
Autorar (criar/publicar)Editor de ExtensõesAdministrador
Instalar (configurar/ligar/remover)Extensões InstaladasSomente superusuário
Distribuir em várias empresasPainel do parceiroParceiro

O que é global: o aplicativo e o seu identificador único. O que é local: a instalação (público, configuração, chave e dados). A mesma extensão instalada em duas empresas são duas instalações separadas.

4. O teste do ciclo de vida (do zero ao uso)

Para não ficar na teoria, executamos a vida inteira de uma extensão de exemplo, com provas em cada etapa:

  1. Completar o rascunho — gravar o arquivo de tela e o manifesto.
  2. Publicar a versão — o artefato vai para o CDN e fica imutável.
  3. Apontar o canal de teste (dev) e instalar para um público restrito.
  4. Conferir na tela — aqui surgiu a primeira lição: um painel de atendimento só aparece para quem atende chats.
  5. Acrescentar um item de barra superior (visível para todos) — nova versão, novo ponteiro, e o item apareceu.
  6. Apontar produção — o endereço público passou a servir a versão nova.
  7. Desmontar — remover a instalação e apagar a extensão (com a lição de que apagar a extensão não remove as instalações).

5. Armadilhas do produto

Filtro vazio = ninguém. Uma lista de inclusão vazia não significa "todos". Sintoma: instala e não aparece para ninguém, sem erro.
Filtro restrito demais. Instalar "só para um usuário" é ótimo para testar — mas quem não casa com o filtro simplesmente não vê a extensão (foi o que aconteceu com um usuário do tipo Agente).
Aparece só em certas telas. Um painel de atendimento não existe para quem não atende chats. Para demonstração, use um item de barra superior.
O identificador global congela na 1ª publicação. Escolha bem o id (fornecedor.extensao): mudar depois = apagar e recriar.
author é objeto, não texto. { "name": "..." }. Texto solto é recusado.
icon é arquivo, não nome de ícone do sistema. Ou aponte para um arquivo da extensão, ou omita (gera aviso, não erro).
Todo url citado tem de existir. Arquivo ausente = publicação recusada.
Publicar não coloca no ar. Publicar congela a versão; apontar o ponteiro (dev/prod) é que coloca em uso.
Versão publicada é imutável. Para corrigir, clone para uma versão nova (o número sobe sozinho).
Remover instalação exige confirmação explícita. Sem ela, a operação só devolve um aviso.
Apagar a extensão não remove as instalações. Elas podem ficar órfãs — remova-as também. E apagar tem alcance externo: afeta outras empresas que a instalaram.
Segredos só são protegidos se declarados. Envie apenas as chaves que o manifesto declara; campos do tipo secret voltam sempre mascarados.

6. Armadilhas da infraestrutura

Produção tem cache (~15 min). O correto é testar no canal de dev (imediato) e só depois mover produção.
Exclusão da CDN não é instantânea sem "purge". Após apagar a extensão, os arquivos somem na hora, mas o manifesto pode continuar respondendo por alguns minutos, por cache de borda.
Falso positivo de CORS. Um verificador pode acusar "sem permissão de acesso" quando a requisição não manda a origem. Confirme com uma chamada que envie a origem antes de acreditar no erro.

7. Armadilhas do projeto do manual

O cabeçalho e o índice são gerados por script. Editar à mão é perdido na próxima execução: registre a página na lista do script e rode-o.
Adicionar uma página muda muitos arquivos. O cabeçalho aparece em todas as páginas, então uma entrada nova regrava o site inteiro. É esperado.
O repositório é público. Nunca cite nome de instância de cliente — nem em texto, nem em imagem.
Capturas precisam ser "PII-safe". A ferramenta não fotografa a barra de endereço, mas o conteúdo pode vazar dados. Revise cada imagem antes de publicar.

8. Tropeços que cometemos (para você não repetir)

  • Procurar a coisa errada no teste. Um item de extensão é um link, não um botão: procurar botão dá "não existe" e leva a conclusão errada. Quando o teste dá negativo, desconfie primeiro do teste.
  • Achar que "não apareceu" era falha da extensão. Era o filtro de público.
  • Publicar sem ter salvado o manifesto. Sempre confira se o passo anterior deu certo antes de seguir.
  • Esquecer a confirmação na remoção. Ler a mensagem de erro resolve — ela diz exatamente o que falta.
  • Deixar o conteúdo de exemplo duplicar numa captura. Revise a saída antes de fotografar.

9. Como o material foi feito

  1. Estudo do estilo — replicar a estrutura e as classes das páginas existentes.
  2. Redação — problema, papéis, conceitos, fluxo, armadilhas, dúvidas comuns.
  3. Capturas reais — automação do navegador, recortes precisos, sem dado sensível.
  4. Registro no menu — lista do script, card na página inicial, README.
  5. Geração — executar o script que reescreve o cabeçalho, cria o índice e atualiza a busca.
  6. Verificação — abrir localmente, conferir imagens, busca e âncoras.
  7. Publicação — commitar e enviar (push).
Guia avulso: para quem não consegue abrir este site, o mesmo conteúdo foi condensado num arquivo HTML único e autossuficiente (imagens embutidas), que funciona até sem internet.

10. Como testamos (método reaproveitável)

  1. Verificações estáticas: todo link/imagem aponta para arquivo existente? Há dependência externa indevida? Toda página recebeu o menu? A busca indexou?
  2. Teste funcional: subir um servidor local e abrir num navegador de verdade — card na página inicial, imagens, busca por palavra, clique no índice, item ativo no menu.
  3. Teste decisivo: abrir o guia avulso com a rede desligada.
  4. Encerrar o servidor de teste — não deixar processo pendurado.

11. Regras de ouro

Separe os três papéis: quem cria, quem instala, quem distribui. Nunca misture.
Teste em dev; só depois mova prod.
Filtro nunca vazio; confira sempre para quem está entregando.
Instale primeiro para um público restrito — é código de terceiro rodando na sessão do atendente.
Publicar = congelar. Apontar = colocar no ar. Rollback = mover o ponteiro.
Atualizar não exige reinstalar: publique e aponte.
No manual: rode o gerador, nunca cite instância, revise capturas, sempre commite e envie.
